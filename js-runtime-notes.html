01
What is JavaScript?
💡

JavaScript is a high-level, dynamically typed programming language used to create interactive and dynamic applications. It runs in browsers, on servers (Node.js), and increasingly in many other environments.

JavaScript code does not directly communicate with the CPU in its original source-code form. It must be processed before a computer can execute it.

📄 JavaScript Source Code
let a = 10;
let b = 20;

console.log(a + b);  // → 30
ℹ️
This code must go through the JavaScript runtime and engine before it can execute. The engine reads the text, understands its structure, compiles it to bytecode, and finally runs it.
🏗
02
What is a JavaScript Runtime?
🔍

A JavaScript Runtime is the complete environment required to execute JavaScript code. It is more than just the engine — it includes all the surrounding infrastructure that makes JS useful in a real environment.

Four Core Components

JAVASCRIPT RUNTIME │ ├── JavaScript Engine │ ├── Processes JavaScript source code │ ├── Executes JavaScript │ ├── Manages memory │ └── Optimizes code (JIT) │ ├── Environment APIs │ ├── Browser APIs (DOM, fetch, timers…) │ └── Node.js APIs (fs, http, net…) │ ├── Queues │ ├── Microtask Queue (Promises, queueMicrotask) │ └── Task Queue (Timers, Events) │ └── Event Loop └── Coordinates asynchronous execution
💡
Key Insight: The runtime handles both synchronous code (via the engine) and asynchronous operations (via APIs + queues + event loop). Neither part alone is sufficient.
⚙️

04
V8 Engine Architecture

V8 is Google's open-source, high-performance JavaScript engine written in C++. It has five major subsystems:

V8 JAVASCRIPT ENGINE │ ├── Code Processing │ ├── Lexical Analysis → Tokens │ ├── Parsing → Grammar / Syntax │ └── AST → Abstract Syntax Tree │ ├── Code Execution │ ├── Ignition → Interpreter │ └── Bytecode Execution │ ├── Optimization │ └── TurboFan → Optimizing Compiler (JIT) │ ├── Execution Management │ ├── Execution Context │ └── Call Stack │ └── Memory Management ├── Memory Heap └── Garbage Collector (Mark-and-Sweep)
🔄
05
Complete JavaScript Code Execution Flow

Every piece of JavaScript code takes this journey from source text to CPU execution:

① JavaScript Source Code
The code written by the developer — human-readable text
② Lexical Analysis → Tokens
The Lexer/Tokenizer breaks code into meaningful units: keywords, identifiers, operators, literals
③ Parsing → Abstract Syntax Tree
The Parser validates grammar and builds a hierarchical tree structure representing the code
④ Ignition Interpreter → Bytecode
Ignition traverses the AST and generates platform-neutral bytecode, then executes it
⑤ Execution Context + Call Stack
Each invocation creates an Execution Context pushed onto the Call Stack
⑥ Runtime Feedback → Hot Code Detection
The engine profiles execution — counting how often code paths run
⑦ JIT Optimization → TurboFan
Frequently executed ("hot") code is compiled by TurboFan into optimized machine code
⑧ Optimized Machine Code → CPU
The CPU executes native machine code directly — maximum performance
📄
06
Step 1 — JavaScript Source Code

Source code is the code written by the developer. It is plain text that follows the JavaScript grammar specification.

📄 Example Source Code
let a = 10;
let b = 20;

function add(x, y) {
    return x + y;
}

console.log(add(a, b));  // → 30
⚠️
The JavaScript engine cannot simply treat the source code as random text. It must first understand its structure through lexical analysis and parsing.
🔤
07
Step 2 — Lexical Analysis
🔍

Lexical Analysis is the process of reading JavaScript source code and breaking it into small meaningful units called tokens. The component performing this work is called the Lexer or Tokenizer.

Tokenization Example

Input
let a = 10;

The lexer identifies each meaningful unit:

┌─────────────┬────────────┐ │ Token Type │ Value │ ├─────────────┼────────────┤ │ Keyword │ let │ │ Identifier │ a │ │ Operator │ = │ │ Literal │ 10 │ │ Punctuation │ ; │ └─────────────┴────────────┘

Common Token Types

Keywords
let const var function return if / else
Identifiers
a user myFunction calculateTotal
Literals
10 (Number) "hello" (String) true / false null
Operators
+ - * / = === !== && || ! typeof
Punctuation
; , . ( ) { } [ ] : ?
ℹ️
Whitespace and comments are generally discarded during lexical analysis — they help humans read code, but the engine doesn't need them after tokenization.

08
Step 3 — Parsing
🔍

Parsing is the process of analyzing tokens according to JavaScript grammar and determining their structural relationship. The component responsible is called the Parser. Its output is an Abstract Syntax Tree (AST).

→

Valid vs Invalid Syntax

✅ Valid — Parser succeeds

❌ Invalid — SyntaxError

🚨
If the token stream violates JavaScript's grammar rules, the parser throws a SyntaxError and execution halts. This happens before any code runs.

09
Abstract Syntax Tree (AST)
🔍

An Abstract Syntax Tree (AST) is a tree-like data structure representing the hierarchical logical structure of JavaScript code. It strips away formatting details (whitespace, comments) and captures only the meaning.

AST Example 1 — Variable Declaration

Source
let a = 10;
VariableDeclaration │ ├── kind → "let" │ └── declarations └── VariableDeclarator │ ├── id → Identifier { name: "a" } └── init → Literal { value: 10 }

AST Example 2 — Function Declaration

Source
function add(a, b) {
    return a + b;
}
FunctionDeclaration │ ├── name → Identifier { name: "add" } │ ├── params → [ Identifier "a", Identifier "b" ] │ └── body └── BlockStatement └── ReturnStatement └── BinaryExpression ├── left → Identifier "a" ├── operator → "+" └── right → Identifier "b"
💡
You can inspect the AST of any JavaScript snippet at astexplorer.net. Tools like Babel, ESLint, and TypeScript all operate on ASTs.
🔥

Step 4 — Interpreter (Ignition)

After the AST is built, V8's interpreter Ignition takes over. Ignition was introduced in V8 2017 to replace a more complex pipeline.

→

→

⚡
Why not compile directly to machine code? Bytecode starts executing faster (no long compilation step), uses less memory, and the profiling data collected during bytecode execution guides better JIT optimizations later.

Ignition Responsibilities

📖
Traverses the AST and generates a sequence of bytecode instructions
▶️
Executes bytecode using a register-based virtual machine
📊

12
Execution Context
🔍

An Execution Context (EC) is the environment in which JavaScript code is prepared and executed. Every piece of code runs inside an execution context.

What an Execution Context Contains

EXECUTION CONTEXT │ ├── Variable Environment variable/binding records ├── Lexical Environment scope chain info ├── Outer Environment Ref link to parent scope ├── this Binding value of `this` └── Code Phase Creation → Execution
🔗
The concepts of Scope, Closures, Hoisting, and this all live inside the Execution Context. Understanding EC is the foundation for mastering these topics.
🗂
13
Types of Execution Context
🌍
Global EC

Created once when the program starts. There is only one Global EC.

🔧
Function EC

Created each time a function is called. Can have many at once on the call stack.

⚡
Eval EC

Created inside eval(). Rarely used; avoid in modern code.

🌍
14
Global Execution Context

When a JavaScript program begins execution, a Global Execution Context (GEC) is created automatically.

JavaScript Program Starts │ ▼ Create Global Execution Context │ ▼ Push GEC onto Call Stack │ ▼ CREATION PHASE (hoist vars, register functions) │ ▼ EXECUTION PHASE (run statements top-to-bottom) │ ▼ Program Ends → GEC popped from Call Stack
🌐
In browsers, the Global EC has window as its global object and this === window at the top level. In Node.js the global object is global.
🎬
15
Creation Phase — Hoisting Behaviour

Before statements execute, JavaScript prepares the execution environment in a Creation Phase. Different declaration types behave differently.

var — Hoisted and Initialized to undefined

var a = 10;
Creation Phase
→
a = undefined
→
Execution Phase
→
a = 10

let — Hoisted but in Temporal Dead Zone

let b = 20;
Creation Phase
→
b exists (TDZ)
→
Exec reaches declaration
→
b = 20

const — Hoisted but in TDZ, must initialize

const c = 30;
// const x;  ← SyntaxError: Missing initializer

Comparison Table

Declaration Hoisted? Initial Value Re-assignable Scope
var ✅ Yes undefined ✅ Yes Function / Global
let ✅ Yes (TDZ) Uninitialized ✅ Yes Block
const ✅ Yes (TDZ) Uninitialized ❌ No Block
function ✅ Yes (full) Full definition ✅ Yes Function / Global

16
Temporal Dead Zone (TDZ)
🔍

The Temporal Dead Zone (TDZ) is the period between entering the scope (where the binding is created) and the point where a let or const declaration is initialized. Accessing the variable in this window throws a ReferenceError.

console.log(a);  // ❌ ReferenceError: Cannot access 'a' before initialization

let a = 10;

console.log(a);  // ✅ 10
Scope Enters
Binding for a is created but uninitialized
⛔ Temporal Dead Zone
Any access to a here throws ReferenceError
console.log(a) ← ReferenceError
This is inside the TDZ
let a = 10 — TDZ Ends
Variable is initialized, now accessible
✅ console.log(a) → 10
Safe to access after initialization
⚠️
Common mistake: Developers sometimes think let is not hoisted. It is hoisted — but unlike var, it is not initialized with undefined. Hence the TDZ.
⬆️
17
Function Declaration Hoisting

Function declarations are fully hoisted — the entire function body is available before execution reaches the declaration.

// Called BEFORE the declaration — works fine!
console.log(add(10, 20));  // → 30

function add(a, b) {
    return a + b;
}

Function Expressions Are NOT Hoisted

console.log(multiply(2, 3));  // ❌ TypeError: multiply is not a function

var multiply = function(a, b) {
    return a * b;
};
// `var multiply` is hoisted as `undefined`
// calling undefined as a function → TypeError
💡
Best practice: Prefer const function expressions or always declare functions before calling them to avoid hoisting-related confusion.
▶️
18
Execution Phase

After the creation phase completes, the Execution Phase begins. Statements are executed in order, and variable assignments happen at this point.

var a = 10;
let b = 20;
const c = 30;
EXECUTION PHASE │ ├── Execute: var a = 10 → a: undefined → 10 │ ├── Execute: let b = 20 → b: TDZ ends → 20 │ └── Execute: const c = 30 → c: TDZ ends → 30
🔧
19
Function Execution Context

Every time a function is called, a brand-new Function Execution Context (FEC) is created and pushed onto the Call Stack.

function add(x, y) {
    return x + y;
}

add(10, 20);  // new FEC created here
Function Call: add(10, 20) │ ▼ Create Function Execution Context │ ▼ Push FEC onto Call Stack │ ▼ Creation Phase ├── x = 10 (parameter binding) ├── y = 20 (parameter binding) └── local variables / inner functions │ ▼ Execution Phase ├── Execute statements └── return x + y → 30 │ ▼ Return value propagated to caller │ ▼ FEC popped from Call Stack │ ▼ Resume previous Execution Context
📚
20
Call Stack
🔍

The Call Stack is a LIFO (Last In, First Out) data structure that tracks all active Execution Contexts. When a function is called, its EC is pushed; when it returns, its EC is popped.

function one() {
    two();
}

function two() {
    console.log("Hello");
}

one();

Stack State During Execution

Peak state

← top
console.log()
two()
one()
Global Context

Unwinding

1️⃣
console.log() completes → Pop
2️⃣
two() completes → Pop
3️⃣
one() completes → Pop
4️⃣
Global Context stays until program ends
💥
Stack Overflow: Infinite recursion causes the stack to exceed its limit, throwing a RangeError: Maximum call stack size exceeded.

23
Garbage Collection
🔍

Garbage Collection (GC) is the automatic process of reclaiming heap memory occupied by data that is no longer reachable. V8 uses a generational mark-and-sweep approach.

Mark-and-Sweep Algorithm

GC Cycle Begins │ ▼ MARK PHASE ├── Start from GC roots (global, stack refs) └── Traverse all reachable objects → mark them │ ▼ SWEEP PHASE ├── Scan heap └── Free memory for all UNMARKED objects │ ▼ GC Cycle Ends

V8 Generational GC

🐣
Young Generation (Scavenger)

Short-lived objects. Collected frequently and quickly. Most objects die young.

🏛
Old Generation (Major GC)

Long-lived objects that survive young gen collection. Collected less frequently.

💡
JavaScript developers do not manually free memory. However, holding onto references unintentionally (memory leaks) can prevent GC from collecting objects.
📊
24
Runtime Feedback

While bytecode executes, Ignition gathers runtime feedback — profiling data that the engine uses to make optimization decisions.

RUNTIME FEEDBACK │ ├── Execution frequency How often is each code path hit? ├── Type information What types do variables hold? ├── Object shapes Property layout (hidden classes) └── Branch outcomes Which branches are taken most?
💡
V8 uses Inline Caches (ICs) and Hidden Classes (Shapes) to track type feedback. Writing monomorphic code (consistent types) allows V8 to optimize more aggressively.
🔥
25
Hot Code
🔍

Hot Code refers to code paths executed frequently enough that the cost of compiling them to optimized machine code is justified by the performance gain.

Code Executes │ ▼ Ignition tracks invocation counter │ ▼ Counter exceeds threshold? │ ┌────┴────┐ │ │ No Yes → HOT CODE │ │ ▼ ▼ Continue Mark for TurboFan optimization Normally │ ▼ TurboFan compiles to machine code │ ▼ Future calls use optimized path
📌
Deoptimization: If runtime behavior contradicts TurboFan's assumptions (e.g., a variable suddenly holds a different type), V8 deoptimizes back to bytecode and re-profiles.
🚀

41
Synchronous vs Asynchronous Code

Synchronous

Tasks run one after another. Each line waits for the previous to finish.

Task 1 → completes Task 2 → completes Task 3 → completes (blocking)

Asynchronous

Long-running operations are handed off to the environment; JS continues.

Start Async Op → hand off to env → JS continues... → Op completes later → Callback runs
// Synchronous — blocks
const data = fs.readFileSync('file.txt');  // waits
console.log(data);

// Asynchronous — non-blocking
fs.readFile('file.txt', (err, data) => {
    console.log(data);  // runs later
});
console.log("continues immediately");
⚡
42
Microtask Queue
🔍

The Microtask Queue holds high-priority asynchronous continuations. After each task, all microtasks are drained before the next task starts.

Sources of Microtasks

MICROTASK QUEUE │ ├── Promise.then() ├── Promise.catch() ├── Promise.finally() ├── queueMicrotask() └── MutationObserver (browser)
Promise.resolve().then(() => {
    console.log("Promise");
});
// Callback goes to Microtask Queue → runs BEFORE next timer/event
📋
43
Task Queue (Macrotask Queue)
🔍

The Task Queue (also called Macrotask Queue or Callback Queue) holds callbacks that become eligible in later event-loop turns. The event loop processes one task per turn, then drains microtasks.

Sources of Tasks

TASK QUEUE │ ├── setTimeout() even with 0ms delay ├── setInterval() ├── User Events click, keydown… ├── I/O Callbacks Node.js fs, net… └── setImmediate() Node.js only
setTimeout(() => {
    console.log("Timer");
}, 0);
// Even with 0ms delay, callback runs in a FUTURE task, not synchronously
🔁

⚙️
JS Engine

Processes source → AST → bytecode → optimized machine code. Manages execution contexts, call stack, heap, GC.

🌐
Environment APIs

Browser/Node provide external capabilities: DOM, network, timers, file system. These handle async work outside JS.

📋
Queues

Microtask Queue (Promises) has priority over Task Queue (timers, events). Microtasks fully drain first.

🔁
Event Loop

Glues everything together. Waits for call stack to be empty, drains microtasks, picks next task. Repeats forever.

JavaScript source code is processed into tokens and an AST by the Lexer and Parser. The Ignition interpreter generates bytecode which executes via Execution Contexts managed on the Call Stack. Frequently executed code is detected as hot code and compiled by TurboFan into optimized machine code for CPU execution. Meanwhile, the surrounding Browser or Node.js environment provides APIs for external and asynchronous operations whose results are queued as microtasks (Promises) or tasks (timers, events), and the Event Loop coordinates their execution when the call stack is clear.
